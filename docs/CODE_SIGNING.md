# Why Windows blocks Vesper (Smart App Control) — and the fix

## What actually happened

Smart App Control (SAC) on Windows 11 blocks **unsigned** code. It has **no per-app
allow-list** and no "Run anyway" button — the only way past it is to switch SAC off.

That is exactly what happened on uninstall: with the NSIS installer, Windows Settings runs
`%LOCALAPPDATA%\Vesper\uninstall.exe`, which is generated by NSIS and is **not**
Authenticode-signed, so SAC refused to run it. Same story for the setup `.exe` on install.

Microsoft's own guidance: developers must sign **every** binary they ship — `.exe`, `.dll`,
temp installer files, scripts **and uninstallers** — with a certificate from a CA in the
Microsoft Trusted Root Program (or Microsoft Artifact Signing, formerly Trusted Signing).

No amount of application code fixes this. Signing is the fix.

## Immediate workarounds (no certificate needed)

1. **Use the `.msi` instead of the `-setup.exe`.**
   Uninstalling an MSI is performed by `msiexec.exe` — a Microsoft-signed Windows component —
   so **the uninstall step is never blocked**. The NSIS `-setup.exe` path is the one that ends
   in an unsigned `uninstall.exe`.
2. **If already installed with the NSIS setup:** uninstall with SAC temporarily off, then
   switch SAC back on. Since KB5083769 (April 2026, Windows 11 24H2/25H2) SAC is a normal
   toggle under *Windows Security → App & browser control → Smart App Control settings* —
   it no longer requires a Windows reinstall to re-enable.
3. **Check what was blocked:** Event Viewer → *Applications and Services Logs → Microsoft →
   Windows → CodeIntegrity → Operational*.

## The permanent fix: free code signing for open source

Vesper is MIT-licensed and public, so it qualifies for **SignPath Foundation**, which signs
open-source projects for free (OV-level certificate, private key stays in their HSM, publisher
shows as "SignPath Foundation"):

1. Apply at <https://signpath.org/apply> — needs: OSI licence (MIT ✅), public repo ✅,
   existing releases ✅, documented functionality ✅, a published code-signing policy,
   and named Author / Reviewer / Approver roles (a solo maintainer can be the Approver).
2. Add a `Code signing policy` section to `README.md`:
   "Free code signing provided by SignPath.io, certificate by SignPath Foundation."
3. In SignPath, create a project + signing policy for the `vesper` repo, then add its
   GitHub Action to the release workflow **after** `npx tauri build`:

```yaml
      - name: Submit signing request to SignPath
        if: env.SIGNPATH_API_TOKEN != ''
        uses: signpath/github-action-submit-signing-request@v1
        with:
          api-token: ${{ secrets.SIGNPATH_API_TOKEN }}
          organization-id: ${{ secrets.SIGNPATH_ORG_ID }}
          project-slug: vesper
          signing-policy-slug: release-signing
          github-artifact-id: ${{ steps.upload.outputs.artifact-id }}
          wait-for-completion: true
          output-artifact-directory: signed/
```

   Sign **all three**: `vesper.exe`, the `.msi`, and the NSIS `-setup.exe`.
   Every release needs one manual approval in SignPath.

Other routes if SignPath declines:

## What changed in Vesper for this

- **No system-tray icon at all.** Closing the main window (or the widget when it is the last
  visible window) stops playback and exits the process. There is no hidden background state,
  so nothing can feel like it is "still installed and running" after you close it.
- **No "close to tray" preference**, and therefore no setting that could silently keep the app
  alive — that preference was the cause of the earlier ghost-playback bug too.
- Bundle metadata now names the publisher (`Shohail Mahmud`) in Add/Remove Programs and in the
  installer's UAC/details pane, instead of an anonymous entry.
- Installer mode stays **per-user** (`currentUser`): no admin prompt, no machine-wide service,
  and it installs into `%LOCALAPPDATA%` alongside the app's data.
